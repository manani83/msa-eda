# 리팩토링 가이드

## 0. 리팩토링 3원칙

### 1) 작게 나누기
- 1 PR = 1 목적 원칙을 지킨다.
- 변경 범위는 가능한 최소화한다.

### 2) 동작 보존
- 리팩토링 전후의 동작이 동일해야 한다.
- 변경 전/후 검증 포인트를 반드시 남긴다.

### 3) 레이어 정렬
- 책임과 경계 위반을 줄이는 방향으로만 개선한다.
- 구조 개선은 레이어 역할을 더 명확하게 만드는 데 집중한다.

---

## 1. 리팩토링 우선순위

다음 항목을 우선적으로 리팩토링한다.

1. 장애 및 버그가 자주 발생하는 구간
    - 예외 처리
    - 로그 추적이 어려운 영역 포함

2. 변경이 잦은 유스케이스
    - 주문
    - 정기구독
    - 물류 연동 등

3. 거대한 클래스 및 메서드
    - 거대 Service
    - 거대 BizImpl
    - 거대 메서드

4. 중복되거나 복잡도가 높은 Mapper SQL
    - 중복 쿼리
    - 복잡한 조건 분기
    - 유지보수 난이도가 높은 SQL

---

## 2. 표준 절차 (팀 공통 순서)

### Step 1. 보호막 만들기
테스트 또는 검증 근거를 먼저 확보한다.

자동 테스트가 어렵다면 최소한 아래 항목을 문서 또는 PR에 남긴다.

- 입력 / 출력 예시
- 핵심 로그 포인트 (변경 전/후 비교 가능해야 함)
- 쿼리 결과의 핵심 필드 값 비교

### Step 2. 안전한 정리
동작 변경 없이 구조만 정리한다.

- 메서드 추출 (`Extract Method`)
- 네이밍 개선
- 중복 제거
- 불필요한 분기 제거 (`Guard Pattern` 적용)

### Step 3. 책임 이동
레이어 기준에 맞게 책임을 정렬한다.

- Controller의 비즈니스 로직은 Biz / Service로 이동
- BizImpl은 흐름 제어와 조합 담당
- Service는 정책 및 상태 전이 담당
- SQL 및 조회 최적화는 Mapper에서 수행
- 단, 정책 로직은 Service에 유지

### Step 4. 데이터 모델 정리
- 전달 객체와 도메인 성격이 섞여 있다면 역할을 분리한다.
- 불필요한 필드 의존을 줄인다.
- 의미가 불명확한 필드명과 모델 구조를 정리한다.

---

## 3. 거대 메서드 분해 체크리스트

거대한 메서드를 분해할 때 아래 항목을 확인한다.

- 입력 검증(가드 로직)을 분리했는가
- 조회 / 계산 / 저장 / 외부 연동 단계를 함수로 분리했는가
- 상태 전이 로직을 별도 함수로 분리했는가
- 예외 메시지와 에러 코드를 정리했는가
- 로그 포인트가 명확하며 재현 가능하게 남는가

---

## 4. 트랜잭션 / 외부 연동 리팩토링 규칙

### 트랜잭션 경계
- 트랜잭션 경계는 BizImpl에 둔다.
- 이는 팀 규칙과 동일하게 유지한다.

### 외부 연동이 포함된 경우
다음 기준을 반드시 명시한다.

- 타임아웃 기준
- 재시도 여부 및 정책
- 실패 처리 방식

### 구조 개선 고려 기준
- DB 트랜잭션 내부에서 장시간 네트워크 호출이 필요한 경우
- 트랜잭션 범위가 과도하게 커지는 경우
- 외부 연동 실패가 전체 처리에 과도한 영향을 주는 경우

### 운영 대응 기준
- 실패 시 추적 가능한 로그를 남긴다.
- 요청 식별자, 주문번호, 연동 키 등 운영 식별자를 반드시 남긴다.
