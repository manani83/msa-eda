# 코드 스타일 및 PR 가이드

## 1. 포맷 / 정적 분석

### 1.1 기본 원칙
- 포맷은 도구가 결정한다.
- 사람의 취향으로 포맷을 수정하지 않는다.
- `"포맷이 마음에 안 든다"`는 이유로 PR 코멘트를 남기지 않는다.
- 도구가 만든 결과를 팀 표준으로 간주한다.

### 1.2 권장 구성
다음 구성을 기본 예시로 사용한다.

- Java: `Spotless` + `google-java-format`
- import 정리 및 정렬
- trailing whitespace 제거
- `Checkstyle` / `Sonar` 최소 규칙 적용

### 1.3 적용 원칙
- 포맷 수정은 수동 변경이 아니라 도구 실행으로 맞춘다.
- 기능 변경 PR에 대규모 포맷 변경을 섞지 않는다.
- 정적 분석 규칙은 팀이 유지 가능한 최소 세트부터 적용한다.

## 2. 코드 작성 규칙

### 2.1 가독성 우선
- 한 메서드는 한 가지 책임만 가진다.
- 중첩 `if`가 3단 이상이면 가드 패턴 또는 조기 반환으로 개선한다.
- 불필요한 추상화는 만들지 않는다.
- 범용 유틸 클래스 남발을 지양한다.
- 재사용보다 현재 문맥에서의 명확성을 우선한다.

### 2.2 네이밍
- `boolean` 변수와 메서드는 긍정형으로 작성한다.
   - 예: `isValid`, `hasStock`, `canCancel`
- 컬렉션 변수는 복수형으로 작성한다.
   - 예: `orders`, `items`
- 이름만 보고 역할과 의미를 유추할 수 있어야 한다.
- 축약어는 팀 내에서 의미가 명확한 경우에만 사용한다.

### 2.3 주석
- 주석은 `"무엇(What)"`이 아니라 `"왜(Why)"`를 설명하는 데 사용한다.
- 코드만 보면 알 수 있는 내용은 주석으로 반복하지 않는다.
- 로직이 복잡하면 주석보다 함수 분리와 의미 있는 이름을 우선한다.
- 오래되었거나 실제 동작과 맞지 않는 주석은 제거하거나 수정한다.

## 3. Controller 스타일

### 3.1 기본 원칙
- Controller는 얇게 유지한다.
- Controller는 요청과 응답의 경계 역할에 집중한다.

### 3.2 책임 범위
Controller는 아래 역할만 수행한다.

- Request 검증
- Request 매핑
- Biz 호출
- Response 매핑

### 3.3 금지 사항
- Controller에서 비즈니스 로직을 처리하지 않는다.
- Controller에서 Service를 직접 호출하지 않는다.
- Controller에서 Mapper를 직접 호출하지 않는다.
- 위 항목은 레이어 규칙 위반으로 본다.

---

## 4. Service 스타일

### 4.1 기본 원칙
- 정책, 상태 전이, 계산 로직은 Service가 책임진다.
- Service는 비즈니스 규칙을 표현하는 계층이다.

### 4.2 책임 범위
Service는 다음 역할을 담당한다.

- 정책 판단
- 상태 전이 처리
- 계산 로직 수행
- Mapper 결과에 대한 정합성 보장

### 4.3 정합성 처리
Mapper 호출 결과에 대해서는 Service에서 아래를 보장한다.

- `null` 처리
- 기본값 처리
- 유효성 검증
- 예외 상황 판단

## 5. MyBatis (SQL) 스타일

### 5.1 조회 원칙
- `SELECT` 컬럼은 필요한 것만 조회한다.
- 불필요한 `SELECT *` 사용을 지양한다.
- alias는 명확하고 일관되게 사용한다.

### 5.2 동적 SQL 원칙
- 동적 SQL이 과도하게 복잡해지면 쿼리 분리를 우선 검토한다.
- 조건 분기가 많아 가독성이 떨어지면 목적별 SQL로 나눈다.

### 5.3 Mapper 메서드 네이밍
Mapper 메서드는 아래 네이밍 규칙을 권장한다.

- `selectXxx`
- `insertXxx`
- `updateXxx`
- `deleteXxx`

### 5.4 추가 원칙
- SQL은 조회, 저장, 수정, 삭제 목적이 드러나야 한다.
- 정책 로직은 SQL이 아니라 Service에 둔다.
- Mapper는 데이터 접근 책임에 집중한다.

## 6. 테스트 스타일

### 6.1 기본 원칙
- 테스트는 가능한 범위에서 점진적으로 확대한다.
- 우선순위는 단위 테스트에 둔다.

### 6.2 우선 대상
다음 로직을 우선적으로 테스트한다.

- 상태 전이 로직
- 정책 로직
- 계산 로직

### 6.3 테스트 네이밍
테스트 메서드명은 아래 형식을 권장한다.

- `method_condition_expected`

예시:
- `cancelOrder_whenAlreadyShipped_thenThrowException`

### 6.4 작성 방식
- `given / when / then` 형태를 권장한다.
- 한 테스트는 하나의 행위와 하나의 기대 결과에 집중한다.
- 테스트 이름만 보고 어떤 상황을 검증하는지 알 수 있어야 한다.

## 7. PR 규칙

### 7.1 기본 원칙
- 1 PR = 1 목적 원칙을 지킨다.
- 기능 변경과 리팩토링은 가능하면 분리한다.
- 기능과 구조 변경을 한 PR에 과도하게 섞지 않는다.

### 7.2 PR 필수 포함 항목
PR에는 최소한 아래 내용을 포함한다.

- 변경 목적
- 검증 방법
   - 테스트 결과
   - 수동 검증 방법

### 7.3 리뷰 원칙
- 리뷰는 스타일 취향보다 동작, 책임, 구조, 리스크 중심으로 진행한다.
- 포맷 관련 지적은 도구 설정 이슈로 다루고, 사람 간 취향 문제로 다루지 않는다.
