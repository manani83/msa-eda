# 애플리케이션 레이어 및 운영 규칙 가이드

## 1. 팀 공통 원칙

### 1.1 동작 보존 우선
- 리팩토링은 기능 변경과 가능하면 분리한다.
- 기능 변경과 리팩토링을 함께 수행하는 경우, 검증 포인트를 반드시 명시한다.
- 변경 전후의 동작이 동일함을 확인할 수 있어야 한다.

### 1.2 레이어 책임 준수
- Controller / Biz / Service / Mapper의 책임을 명확히 구분한다.
- 각 레이어는 자신의 책임 범위를 침범하지 않는다.
- 책임이 섞이면 우선 정리 대상로 본다.

### 1.3 최소 변경 원칙
- 필요한 범위만 수정한다.
- 관련 있어 보인다는 이유만으로 주변 구조까지 확장 리팩토링하지 않는다.
- 한 번의 변경은 목적이 분명해야 한다.

### 1.4 계약 안정성
- 프론트, 레거시, 외부몰, 외부 시스템과 연결된 응답/필드를 변경할 경우 영향 범위를 명시한다.
- 필드명, 타입, 응답 구조, 상태값, 코드값 변경 시 반드시 사전 검토한다.
- 계약 변경은 내부 구현 변경보다 더 높은 수준의 리스크로 취급한다.

### 1.5 운영 친화적 코드
- 운영 중 장애를 추적할 수 있도록 로그, 에러 코드, 재현 가능성을 확보한다.
- 예외 발생 시 원인 파악이 가능해야 한다.
- 운영 대응이 어려운 코드는 구조적으로 개선 대상이다.

## 2. 레이어 책임 정의

> 아래 규칙은 필수 준수 항목이다.

### 2.1 Controller

#### 책임
- 요청 DTO 매핑
- 응답 DTO 매핑
- 파라미터 검증
    - Bean Validation
    - 필요 시 추가 검증
- 인증 / 인가 확인
- Biz 호출
- 응답 / 에러 매핑

#### 금지
- DB 접근
- Mapper 직접 호출
- 비즈니스 규칙 구현
    - 정책
    - 가격 계산
    - 상태 전이
- 트랜잭션 처리

---

### 2.2 Biz / BizImpl

#### 책임
- 유스케이스(업무 시나리오) 조합 및 오케스트레이션
- 트랜잭션 경계 설정
- Service 호출 순서 및 흐름 제어
- 복수 Service를 조합한 업무 흐름 구성

#### 금지
- SQL / Mapper 직접 호출
    - 원칙적으로 데이터 접근은 Service에서 처리한다.
- 화면 또는 외부 계약 중심 DTO에 과도하게 의존
- 화면 입출력 구조를 기준으로 내부 비즈니스 흐름을 설계하는 방식

#### 권장
- Controller에서 내부 모델로 변환한 뒤 Biz로 전달하는 구조를 권장한다.

---

### 2.3 Service

#### 책임
- 비즈니스 규칙 처리
    - 정책
    - 상태 전이
    - 계산
    - 검증
- 데이터 접근
    - Mapper 호출
    - 조회 결과 변환
    - 정합성 보장
- 공통 로직 재사용
- 도메인 중심 로직 응집

#### 금지
- HTTP 응답 스펙 결정
- 화면 전용 데이터 가공 로직 집중
- 과도한 View 모델링
- Controller 책임에 해당하는 응답/상태코드 판단

---

### 2.4 Mapper (MyBatis XML)

#### 책임
- 데이터 조회 / 저장
- SQL 작성
- 필요한 컬럼만 조회
- 정확한 결과 매핑

#### 금지
- 비즈니스 규칙을 SQL 내부에 숨기는 방식
- 정책 로직을 SQL 조건으로 과도하게 처리하는 방식
- 복잡도가 과도한 동적 SQL
- 유지보수가 어려운 거대 쿼리

#### 원칙
- 정책은 Service에서 처리한다.
- 동적 SQL이 지나치게 복잡해지면 목적별로 쿼리를 분리한다.

---

## 3. 네이밍 규칙

### 3.1 패키지
- 패키지명은 소문자로 작성한다.
- 의미 단위로 분리한다.
- 기술 기준보다 업무/도메인 기준 구성을 우선 검토한다.

### 3.2 클래스 네이밍
- Controller: `*Controller`
- Biz 인터페이스: `*Biz`
- Biz 구현체: `*BizImpl`
- Service: `*Service`
- Mapper: `*Mapper`

### 3.3 DTO 네이밍
- Request DTO: `*Request`
- Response DTO: `*Response`

### 3.4 내부 모델 네이밍
- 입력 모델: `*Command`
- 결과 모델: `*Result`

### 3.5 메서드 네이밍
- 메서드는 `동사 + 목적어` 형태로 작성한다.

예시:
- `createOrder`
- `cancelOrder`
- `getOrderDetail`

## 4. DTO / 모델 흐름 규칙

### 4.1 기본 원칙
- Mapper 반환 타입은 팀 기준으로 통일한다.
    - 예: Entity / VO / Map
- 반환 타입의 형태와 무관하게 Service가 최종 책임을 가진다.

### 4.2 Service 책임
Service는 Mapper 결과에 대해 아래를 보장해야 한다.

- 검증
- 변환
- 정합성 확인
- 기본값 처리
- null 처리
- 예외 판단

### 4.3 흐름 원칙
- 외부 요청 모델과 내부 처리 모델은 필요 시 분리한다.
- 외부 계약용 DTO가 내부 전 레이어를 관통하지 않도록 주의한다.
- 화면 중심 DTO보다 업무 의미가 드러나는 내부 모델을 우선한다.

---

## 5. 예외 / 에러 처리 규칙

### 5.1 기본 원칙
- 예외는 숨기지 않는다.
- 예외는 운영과 개발 모두가 이해할 수 있는 형태로 남겨야 한다.
- 사용자 메시지와 내부 원인 메시지는 구분한다.

### 5.2 처리 기준
- 비즈니스 예외와 시스템 예외를 구분한다.
- 예외 상황에는 일관된 에러 코드 또는 식별 가능한 기준을 사용한다.
- 동일한 성격의 실패는 동일한 처리 방식과 메시지 체계를 유지한다.

### 5.3 레이어별 원칙
- Controller는 예외를 HTTP 응답 또는 표준 응답 형태로 변환한다.
- Biz / Service는 예외를 발생시키거나 필요한 범위에서 래핑하되, 원인을 숨기지 않는다.
- Mapper/DB 예외는 그대로 노출하지 말고 필요한 경우 서비스 맥락에 맞게 처리한다.

### 5.4 금지 사항
- `catch` 후 로그만 남기고 정상 흐름처럼 처리하는 방식
- 의미 없는 범용 메시지 사용
    - 예: `"에러 발생"`, `"처리 실패"`
- 원인 정보 없이 예외를 재던지는 방식

### 5.5 권장 사항
- 주문번호, 회원번호, 요청 ID 등 추적 가능한 정보를 함께 남긴다.
- 운영에서 바로 원인 파악이 가능하도록 메시지와 코드 체계를 정리한다.

---

## 6. 트랜잭션 원칙

### 6.1 기본 원칙
- 현재 구조 기준으로 트랜잭션은 BizImpl에서 설정한다.
- 트랜잭션 경계는 유스케이스 단위로 잡는다.

### 6.2 조회성 처리
- 조회성 작업은 `readOnly = true`를 사용한다.

### 6.3 변경성 처리
- 생성, 수정, 삭제 등 변경 작업은 기본 트랜잭션으로 처리한다.
- 하나의 업무 시나리오 안에서 데이터 일관성을 보장해야 한다.

### 6.4 외부 호출 포함 시 원칙
외부 호출이 포함되는 유스케이스는 장시간 블로킹을 피해야 한다.

가능하면 아래 방식으로 처리한다.

- DB 작업과 외부 호출을 단계적으로 분리
- 장시간 네트워크 호출을 트랜잭션 내부에 오래 유지하지 않도록 개선
- 최소한 아래 기준을 명시
    - 타임아웃
    - 재시도
    - 실패 처리 방식

### 6.5 주의 사항
- 트랜잭션 범위가 과도하게 넓어지지 않도록 한다.
- 외부 시스템 장애가 전체 DB 트랜잭션에 과도한 영향을 주지 않도록 설계한다.

## 7. 로깅 / 운영 규칙

### 7.1 기본 원칙
- 로그는 장애 분석과 운영 대응을 위한 정보여야 한다.
- 재현 가능한 수준의 맥락 정보를 남긴다.
- 불필요한 로그 남발보다 핵심 포인트를 명확히 남기는 것을 우선한다.

### 7.2 필수 로그 기준
다음 항목은 필요한 범위에서 로그에 포함한다.

- 요청 식별자
- 주문번호 / 회원번호 / 외부 연동 키
- 처리 단계
- 성공 / 실패 여부
- 예외 메시지
- 소요 시간(필요 시)

### 7.3 로그 위치
- 유스케이스 시작 / 종료 지점
- 외부 연동 호출 전 / 후
- 주요 상태 전이 시점
- 운영 이슈가 자주 발생하는 조건 분기
- 예외 발생 지점

### 7.4 금지 사항
- 개인정보, 민감정보를 그대로 로그에 남기는 행위
- 의미 없는 반복 로그
- 운영에서 식별 불가능한 로그 메시지

### 7.5 권장 사항
- 동일한 업무 흐름에서 로그 형식을 일관되게 유지한다.
- 운영자가 검색 가능한 키워드 중심으로 로그를 남긴다.
- 장애 분석에 필요한 최소 맥락을 항상 확보한다.

## 8. AI 도구 사용 규칙

### 8.1 기본 원칙
- AI가 생성한 코드는 작성자가 책임진다.
- AI 사용 여부와 관계없이 동일한 리뷰 기준을 적용한다.
- 리뷰 통과 전까지는 사람이 최종 검증해야 한다.

### 8.2 PR 필수 포함 항목
AI 도구를 사용한 경우 PR에는 아래 항목 중 최소 1개 이상 포함한다.

- 변경 목적
- 영향 범위
- 검증 포인트
- AI 사용 여부
- 핵심 프롬프트 링크 또는 요약

### 8.3 운영 원칙
- AI 출력 결과를 그대로 신뢰하지 않는다.
- 팀 규칙, 레이어 책임, 도메인 정책에 맞는지 반드시 검토한다.
- 생성된 코드가 기존 계약, 로그, 예외 처리, 운영 기준을 위반하지 않는지 확인한다.
